# 커밋 메시지 규칙

커밋 제목은 `[헤더] 설명` 형식으로 작성한다. 헤더 뒤에는 공백 한 칸을 넣고 변경 내용을 구체적으로 적는다.

| 헤더 | 용도 |
| --- | --- |
| [TEST] | 테스트 코드 |
| [MERGE] | 머지 관련 |
| [BUILD] | 빌드 관련 |
| [INIT] | 프로젝트 초기 설정 |
| [DOC] | 주석 수정, 리드미 수정 등 문서 변경 |
| [REFAC] | 리팩토링, 파일 구조 수정, 프레임워크 수정 등 |
| [FIX] | 버그 픽스 |
| [MOD] | 기능 수정 |
| [ADD] | 에셋 추가, 씬 추가 등 단순 추가 |
| [FEAT] | 기능 구현 |

## 작성 예시

- `[FEAT] 스프레드시트 스탯을 SO로 가져오고 Play 중 자동 갱신`
- `[MOD] 적 체력 갱신 시 기존 피해량 유지`
- `[FIX] 적 스탯 변경 후 체력 초기화 오류 수정`
- `[DOC] 커밋 헤더 규칙 문서화`

## 커밋과 푸시

- 앞으로 작성하는 모든 커밋 메시지에 이 규칙을 적용한다. PR의 squash/merge 커밋 제목에도 적용한다.
- 작업 범위에 해당하는 변경만 확인·검증한 뒤 커밋하고 해당 기능 브랜치로 푸시한다. 관련 없는 로컬 변경은 포함하지 않는다.
- main과 develop에는 직접 푸시하지 않는다. 기능은 develop 대상 PR로 제출하고 최소 1명 승인 후 병합한다.
- `git config core.hooksPath .githooks`로 로컬 훅을 활성화한다. commit-msg 훅은 헤더 형식을, pre-push 훅은 브랜치 규칙을 검사한다.
- 로컬 훅은 원격 브랜치 보호 규칙을 대체하지 않는다.
